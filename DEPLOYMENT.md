# Cloud deployment

This setup hosts the React/Vite frontend on Vercel and the FastAPI backend on Render. It keeps the backend on one long-running instance because SecureTransfer currently keeps active sessions and undelivered ciphertext in process memory.

## Before deploying

- Publish this repository to GitHub from GitHub Desktop.
- Create a Vercel account and a Render account.
- The Render Blueprint includes a persistent disk and uses the `starter` service plan. Render requires a paid service plan for persistent disks. The disk keeps the SQLite database, generated identity keys, and received files across restarts.

This is a small single-instance demo deployment. Render disks cannot be shared between multiple service instances. Active sessions and queued messages are still held in memory: they are lost on a backend restart or redeploy, and users may need to open a new secure session. Do not use this setup as a production service for important data. Production use needs durable session and inbox storage, backups, and a security review.

## 1. Deploy the frontend on Vercel

1. Import the GitHub repository into Vercel.
2. Set **Root Directory** to `frontend`.
3. Use the Vite defaults: build command `npm run build`, output directory `dist`.
4. Deploy once to obtain the frontend's production URL. API calls will not work until the backend URL is configured below.

The included `frontend/vercel.json` routes browser page requests to the SPA entry point.

## 2. Deploy the backend on Render

1. In Render, create a **Blueprint** from the same GitHub repository. Render reads `render.yaml` from the repository root.
2. When prompted for `SENTINEL_ALLOWED_ORIGINS`, enter the exact Vercel production origin, for example `https://your-app.vercel.app` (no path or trailing slash).
3. Review the plan and persistent disk before applying the Blueprint. The API is public on its Render URL; keep `SENTINEL_RATE_LIMIT_DISABLED` set to `0` and leave encryption demo logging disabled.
4. Wait for the service health check at `/health` to pass. Copy the backend's `https://...onrender.com` URL.

## 3. Connect the frontend to the API

In Vercel, open the frontend project's environment variables and set:

```text
VITE_API_BASE_URL=https://your-api.onrender.com
```

Do not add a trailing slash. Redeploy the frontend so Vite includes the value in its production build.

If you use Vercel Preview deployments, add each preview origin you want to use to Render's `SENTINEL_ALLOWED_ORIGINS`, comma-separated. Use only origins you control.

## Administrator login and audit records

In the Render service's **Environment** settings, set both `SENTINEL_ADMIN_USERNAME` and `SENTINEL_ADMIN_PASSWORD`. Keep the password in Render's secret environment variable field; do not commit it to GitHub. Use a strong password no longer than 72 UTF-8 bytes. The service creates or updates this administrator account at startup. Admin accounts cannot be self-registered, and the Admin login endpoint rejects ordinary users.

The audit API and message-log API require an admin account on the server, not just an admin-looking frontend. Ordinary user sessions cannot fetch the audit log or ciphertext log endpoints. Message records contain sender/recipient, sent/received timestamps, ciphertext, its SHA-256 digest, nonce, AES-GCM authentication tag, and a server-generated Ed25519 audit attestation. This attestation is signed by the server; it is not a digital signature generated by the sender's device. Plaintext is not stored in these message records.

The free Render service uses ephemeral storage, so its SQLite users, audit logs, message records, and audit signing key are lost on redeploy, restart, or spin-down. The admin account is recreated from the two environment variables at startup, but old logs cannot be recovered after the database is lost.

## Local development

Leave `VITE_API_BASE_URL` unset locally. Vite will continue proxying API calls to `http://127.0.0.1:8000`.
